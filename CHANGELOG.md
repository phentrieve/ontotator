# Changelog

All notable changes to this project are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added

- Annotation view: in a low window the open ontology tree takes the right column (#521). In the three-column layout, when the layout is lower than the annotation panel's 160 px and the tree's useful 420 px together (580 px; it switches back only at 604 px), the annotation panel shrinks to one line above the tree: the marked words and the term of the finding, and **Show finding**, which brings the whole panel and the divider back until the tree is closed. The tree's rows then get 70 % of it (ten rows at 1280 × 600, five before). On a phone in landscape (701–1024 px wide, up to 560 px high) the tree stands in place of the panel beside the text; closing it brings the panel back. A focus in the panel that folds away moves to **Show finding** or into the tree, and the change is announced. 1440 × 900, 1440 × 700 and the two stacked columns are unchanged.
- Dark theme (#492). Ontotator follows the light or dark setting of the device, and **Profile** › **Appearance** has the setting **Theme** with **System**, **Light** and **Dark**. The choice is kept in the browser (not in the account), applies at once, also to the login page, and is applied before the page is drawn, by a small script file of its own (`/theme.js`), because the Content-Security-Policy allows no inline script. Every colour has a dark value in `frontend/src/styles/tokens.css`; form fields and scrollbars follow through `color-scheme`. Marks in the text, person lanes, **Show changes**, notices, badges and focus rings keep WCAG AA contrast in both themes: a unit test checks the colour pairs that are used together, a browser test checks the main screens in dark at 1440 px and 390 px. Screenshots and handbook images stay light. No API change, no migration.
- Translations: a list of translation reviews for leads (#483). **Translation reviews** on **Progress** opens one row per submitted translation review, newest first, and one per review that is assigned but not submitted: the text (case ID, language, version), the reviewer, the decision, the clinical flag, the categories, the rationale, the number of changed passages and the submitted date. The rationale is shown for accepting reviews too, so a remark a reviewer leaves there, for example about the source, reaches the lead. **Person**, **Decision**, **Language** and **Order** filter and sort on the server, 25 reviews per page; the address keeps them. **Compare versions** in the row of a review accepted with corrections opens the text view with the reviewed and the corrected version side by side, ready for **Show changes**; other rows open the reviewed text. New `GET /api/v1/projects/{key}/translation-review-list` (scope `read`; leads and system administrators only, everyone else gets 403) with `reviewer` (pseudonym), `decision` (also `open`), `language`, `sort` (`-submitted`, `submitted`), `limit` (at most 200) and `offset`; it returns `reviews`, `total` and the choices of the filters (`reviewers`, `languages`). `changed_passages` is counted on the server by words: a replaced wording is one passage, a change of spaces only is none, and it is null when the texts differ too much to count. `GET …/translation-reviews` is unchanged. No migration.
- Annotation view: in the three-column layout, the divider above the docked ontology tree sets its height (drag, or `↑` / `↓` on the focused divider; double-click resets). The tree keeps at least 220 px and leaves the annotation panel at least 160 px, at every window height. The height is kept per user in the browser. `SidebarResizer` has a horizontal mode for it, and `Esc` that gives up a drag of a divider no longer also clears the selection.
- Ontology tree: **Hide details**, next to the name of the selected term below the tree, keeps only its name and code on one line, so the rows of the tree get the room (about 20 px in a 600 px high window, 67 px at 900 px); **Show details** brings the rest back. The choice is kept per user in the browser.
- Guidelines: a version can carry the project's own version of the document (#487). **Settings** › **Guidelines** has one more optional field when publishing, **Your version of the guideline (optional)** (for example *3.1*; one line, up to 40 characters). It is stored with the version and shown before the upload number wherever the version is named: *Guidelines 3.1 (v2)* in the task, the reader and the settings, *Guidelines updated to 3.1 (v2)* in the notice, *Project guidelines 3.1 (v2)* on My tasks, and *Guidelines 3.1 (v2) (current: 3.2 (v3))* on submitted results and translation reviews. Without it everything reads as before (*Guidelines v2*). The upload number stays the identifier: `expected_latest_version`, withdraw, republish, the stamp on a submission and the export reference `urn:ontotator:{project}:guidelines:v{n}` are unchanged. The label cannot be edited later and stays when the version is withdrawn; **Republish** fills it in from the earlier version. API: `POST /api/v1/projects/{key}/guidelines` takes the optional form field `label` (refused with `GUIDELINE_NOTE_INVALID`, `field: label`); the version views carry `label`, a task's `guideline` and `guideline_notice` carry `label` and `to_label`, and each `guideline_version` stamp of a submission or translation review comes with `guideline_label`. The translation review export (`ontotator-translation-review/v1`) gets the additive field `guideline_label` after `guideline_withdrawn`; the final export (`index.csv`, `guideline_ref`) is unchanged. MCP: `publish_guideline` takes an optional `label`; `list_guidelines` returns it. Migration 0048 adds the nullable column `guideline_versions.label`; a project archive carries it.
- Translation review: the confirmation of **Submit review…** names the typography hints of the text to be saved (#484), for example *2 typography hints in your text: double space, doubled full stop.* **Show them** lists each place with a little text around it, spaces drawn as dots. The line blocks nothing. It is read from the saved draft with the new `GET /api/v1/translation-reviews/{assignment_id}/draft/typography-hints` (scope `read`; rule codes and positions, as for a text version; only the reviewer of the task).
- Documents: the badge **Typography hints** on a text whose newest version has hints, and the filter **Typography hints** under **Flags** (`flags=typography_hints`), so a lead finds such texts before assigning (#484). Rows of `document-rows` carry `typography_hints` (the number of hints). Hints are still not stored: the count of a version is computed once per server process and kept by text hash.
- Typography hints: the new rule `DOUBLE_FULL_STOP` finds two full stops in a row; an ellipsis (*...*, *…*) and a path (*../*) are left alone (#484).
- Translation review: a check for names the translation added in brackets (#484). When the reviewed version has more passages in round or square brackets than its source, the checks band reads *More passages in brackets than in the source: 3 in the translation, 1 in the source*, and **Details** lists the passages the source does not have in this form. Ontotator computes it when the review is opened, for every version; it is not a check of the translation run, is not counted in **My tasks** and asks for no rationale. The review workspace carries it as `added_brackets`.
- MCP: a queried translation is decided without the browser, and a version is uploaded without retyping the text (#485). The new tool `decide_translation_query` (scope `project-admin`) is the lead's decision on a translation review submitted as **Query**: `decision: reviewer_text` saves the text the reviewer proposed as the next version, accepted, with optional `replacements`; `decision: unchanged` accepts the version as it is and needs an `answer`. The dry run says whether the query can be decided, with the reason and the next step if not, and counts what the text changes against the version; the confirm needs the dry run's `preview_token` and changes nothing when the text, the review or an argument differs from the dry run. `upload_translation_version` takes `from_review_id` in place of `text` (the text a translation review of that version proposed; reading it needs the scope `read` as well) with `replacements`, each of which must match exactly once and is named if it does not; its dry run now counts the changes against the current version (`passages_changed`, `inserted_characters`, `deleted_characters`). In both dry runs the changed passages (`diff`) and the reviewer's question are returned only when the MCP server runs with `ONTOTATOR_MCP_READ_CONTENT=1`; the whole text never. The refusals `QUERY_DECISION_NOT_AVAILABLE` (per reason) and `VARIANT_REVIEW_STALE` come with a sentence that names the next step. The tool descriptions say which tool to use when: a query → `decide_translation_query`; a text made or reviewed outside Ontotator → `upload_translation_version` and `accept_translation_version`.
- Translations: the lead decides a translation review submitted as **Query** (#483). **Resolve…** on a queried text has two more items. **Accept the reviewer’s text…** shows the text the reviewer proposed, which the lead may still change, with its changes against the version (*Changes to v1 · 2 passages changed*); it becomes the next version, accepted. **Answer and accept the version as it is…** accepts the version unchanged. Both take an **Answer to the reviewer** (required for the second), are recorded as the lead's decision on the query, not as *reviewed outside Ontotator*, and are audited (`translation.query_decided`). The version row reads *Accepted: decision on the query of Ana Weber (ann-0003), the reviewer’s text taken, …· Answer: …*, **History** has a line (*query decided by you, the reviewer’s text taken, v1 → v2, 18 Nov, 10:12: …*), and the row goes on with the accepted version. The reviewer sees *Answer from the lead* at the submitted review in **My tasks** and reads the decision and the answer in the task. New endpoints `GET` and `POST /api/v1/projects/{key}/documents/{document_id}/query-decision` (scope `project-admin`; body `kind` `reviewer_text` or `unchanged`, `expected_text_sha256`, `expected_review_id`, `text` for `reviewer_text`, `answer`); refusals `QUERY_DECISION_NOT_AVAILABLE` with `reason` `already_decided`, `not_a_query`, `review_open`, `not_newest`, `discarded`, `unchanged` or `answer_required`, and `VARIANT_REVIEW_STALE`. Rows carry `versions[].query_decision`, a review workspace `query_answer`, a task `query_answered_at`. Migration 0049 adds the append-only table `translation_query_decisions`; a project archive carries it.
- **Fix typos…**: **What did you fix?** has the choice **Removed addition**, for words the machine added that the source does not have, for example a synonym in brackets (#483).

### Changed

- Navigation: the account is in a user menu at the top right, and Administration is its own area (#510). The button with your name, pseudonym and roles opens the menu with **Profile**, **My technical reports**, **Technical problem…**, the **Theme** (**System**, **Light**, **Dark**; the setting on **Profile** › **Appearance** stays and shows the same choice) and **Log out**, which asks about unsaved changes as before. System administrators see a gear next to it: it opens **Administration** with its own sidebar (**Users**, **Ontologies**, **Technical reports**, **Server settings**, **Back to Projects**); the gear carries the count of open technical reports. **New project** is a button on the **Projects** page. The work sidebar keeps the project switcher (`Alt+P`), **My tasks**, **Projects** and, for leads, the pages of the current project; an administrator without a project now sees **Projects** too. The addresses of all pages are unchanged (`#/admin/users`, `#/admin/ontologies`, `#/admin/reports`, `#/admin/settings`, `#/projects/new`, `#/me`). In the editor and on a phone the user menu (there with your initials) and the gear stay in the header; **Report a technical problem…** stays in **More** and on the error screens. No API change, no migration.
- MCP server: answers are short by default and shaped the same way everywhere (#471). **These change what existing agents and scripts receive.** `list_texts` returns at most 100 texts in a short form and pages with `limit` and `offset` (`next_offset`); `fields` names what else to return (`["all"]` for everything). `project_audit` returns 50 events per call without their `details` (`include_details`). `project_overview` leaves out `links` (`include_links`). Tools that returned a bare list return `{"items": [...], "count": n}`, so an empty result is an answer: `list_projects`, `list_ontologies`, `list_ontology_files`, `list_project_templates`, `list_uploads`, `list_people`, `list_users`, `find_people`, `list_problem_reports`, `list_translation_reviews`, `list_annotation_versions`. The text of every answer is JSON without indentation.
- MCP server: a person is `username`, `display_name` and `pseudonym` in every tool result (#471), where it was the pseudonym in one tool and the display name in another. A name the server does not return is `null`; the audit names nobody's login. `consolidation` is accepted as a task name where `review` means a consolidation (`tasks` of `reopen_texts` and `withdraw_open_tasks`); `review` still works. Every `document_id` argument says that a case ID is not one.
- MCP server: "which texts are over the limit?" has an answer (#471). `list_texts` shows each text's `annotations_per_text` and `over_limit` and filters with `over_limit=true`; `annotation_target_preview` names the texts, not only their number.
- MCP server: `project_overview` splits `workload[].submitted` by task; `list_translation_reviews` with `include_text` takes `diff=true` and then returns the changed passages in place of the reviewer's full text; `upload_translation_version` says that `note` is shown to a translation reviewer of the version as well as on the lead's row (#485).
- API: the person references in the Documents rows and in the previews of the bulk actions (reopen, withdraw, new round, pause, annotation mode, undo of a final-result change) have `username` (#471, `MemberRefView`): for a lead and of a current member of the project, as the members list shows it; otherwise `null`. Every other person reference is unchanged and has no such field: problem reports, the audit and the job list name nobody's login. `GET …/work-plans/annotation-target-preview` returns `rows` (case, language and number of annotators of each text over the target) next to `rows_over_target`. Each entry of `workload` in `GET …/progress` has `translation_reviews_submitted`, `annotations_submitted` and `reviews_submitted` next to `submitted` (#485).
- MCP server: `ontotator-mcp` has the version of the release it comes from, no longer `0.1.0` in every release (#486). `ontotator-mcp --version`, the User-Agent of its requests and `whoami` show it; a release sets it with the app version (CONTRIBUTING, **Releases**; an MCP test fails while they differ). `whoami` returns the version of the Ontotator server (`server`) for every kind of token, a project token included (#485), next to the MCP server's own (`mcp_server.version`), and a `warning` when the two differ: a running MCP process keeps the code it started with, also after the package was upgraded.
- MCP server: the tool descriptions say that `ONTOTATOR_MCP_READ_CONTENT=1` is a setting of this MCP server in the MCP client's configuration, not of the Ontotator server (#485); `whoami` reports whether the content tools are on (`mcp_server.content_tools`).
- API: `POST …/guidelines` without `expected_latest_version` while versions exist still answers 409 `GUIDELINE_VERSION_CONFLICT`, now with `details.reason` `expected_version_missing` next to `latest_version` (#486). The MCP server reads it as "the request named no version; restart an older MCP server" instead of "another version was published meanwhile; repeat".
- MCP server: `change_note` of `publish_guideline` and `reason` of `withdraw_guideline` state their limit (one line of at most 280 characters; annotators see it) and refuse a longer text before sending; `GUIDELINE_NOTE_INVALID` names the limit (#486).
- MCP server: refusals say what to do next (#471). `start_consolidation` names the open consolidation task of the person (it no longer advises a dry run the tool does not have) and the missing consolidator role; its description no longer promises the role to everyone. `ASSIGNEE_ROLE_MISSING`, `ANNOTATIONS_PER_TEXT_REACHED`, `VARIANT_REVIEW_STALE`, `NOT_A_TRANSLATION`, and `BULK_UNDO_STALE` and `VERSION_UPLOAD_NOT_AVAILABLE` with each of their reasons, end with the next step; a code is no longer repeated as its own details. `assign_texts` gives each refused row a `hint` and counts refused rows in `warning`.
- MCP server: the dry run of `start_new_round` reports an open consolidation (`blocked`) instead of promising a round the confirm refuses (#471). Skip and keep reasons of the bulk tools name the tool or argument (`include_started=true`, `withdraw_final_result`, `release_texts`, `update_work_plan`) instead of buttons of the web interface.
- MCP server: the `preview_token` of `reopen_texts`, `withdraw_open_tasks` and `start_rounds` also stands for the reason, so a confirm with another reason than the dry run's is refused (#471). A cut or mistyped `preview_token` is refused as such; the note of a stale answer also names a token of another dry run. `start_rounds` with `clean_restart` and no reason, and `upload_translation_version` for a machine translation without `provider`, fail at the dry run.
- **Annotators per text** has no built-in maximum (#457; it was 20). A lead sets any number from 1, as the project setting (**Settings** › **Workflow**) and as a text's own value (assign dialog, info button). The hint below the field is *Upper limit; fewer is fine.* again. The API accepts any whole number from 1 up to the column's type (2147483647) for `PATCH …/settings`, both `annotations-per-text` routes and the `annotation-target-preview`; the MCP tools `set_annotations_per_text` and `annotation_target_preview` no longer stop at 20. Migration 0050 replaces the two check constraints (`BETWEEN 1 AND 20` becomes `>= 1`); no row changes. Its downgrade refuses while a project or a text has more than 20.
- New optional server setting `ONTOTATOR_MAX_ANNOTATIONS_PER_TEXT` (#457): the most annotators per text a lead can set on this server, for a project and for a single text; unset means no limit. A larger number is refused with the new code `ANNOTATIONS_PER_TEXT_ABOVE_MAXIMUM` (HTTP 422), which names the maximum; the web interface says *This server allows at most 8 annotators per text. Enter 8 or less.* The settings page names the maximum below the field (*This server allows at most 8.*), the project settings return it as `annotations_per_text_max`, the assign preview as `max_per_text`, and the MCP tool `project_overview` as `annotations_per_text_max`. A number saved before the maximum was set stays. See "Annotators per text" in [docs/operations.md](docs/operations.md).
- One consolidation merges at most twice the annotators per text of its text, and never fewer than 40 submissions (#457; the bound was a fixed 40). More sources are refused with `ROUND_INPUT_INVALID` and a message that names the bound (before: a validation error of the request body). The MCP tool `start_consolidation` no longer stops at 40.
- A person's tasks follow the order of assignment (#488, options 1 and 3). **My tasks** and the editor's next task were ordered by status and then by the text's upload position, so a lead who assigned texts in a planned order did not get that order. Within a status the tasks are now in the order of assignment (assignment ID); translation reviews and consolidations use the same list. Bulk assignment creates the tasks in the order of its input: the rows of `POST /api/v1/projects/{key}/assignments` (MCP `assign_texts`, **Distribute evenly…**), and for `POST …/assignments/batch` the order of `sort`, which has the new value `given` for the order of `case_ids` (MCP `distribute_texts` sends it when it is given `case_ids`; the assign dialog keeps the order of the **Documents** list). A reopened task still moves to the **Reopened** tasks at the top; a task that follows a corrected text keeps its ID and its place; a task continued on a new version with **Handle text change…** takes the place of the task it continues; a reassigned task and work carried from a submission are new tasks and come last. **Move to front** still puts texts first: the tasks already assigned on these texts come first within their status; tasks assigned afterwards follow the order of assignment. The assign dialog, **Propose distribution**, the handbook and the descriptions of `assign_texts` and `distribute_texts` say in which order a person sees the tasks. Annotators cannot sort **My tasks**; its project filter and status tabs keep the order. No migration.
- **Show changes** (text view comparison, **Show changes since**, the changed passages of a carried round) marks and counts a changed number of spaces, for example a double space a reviewer typed or a removed space at the end (#483). A change of line breaks only, or of the kind of space (a non-breaking space for a space), is still not marked.
- Handbook: a problem in the source that does not affect the translation is no **Query**; accept the translation and put the remark in the **Rationale** (#483). **Accept this version…** is no longer described as the way to close a query.
- MCP server: a consolidator can read the inputs of their own consolidation task, also with **Hide annotator names during consolidation** on (#471). `list_my_tasks` lists the token owner's tasks with their `assignment_id`; `get_consolidation_inputs` (a content tool, `ONTOTATOR_MCP_READ_CONTENT=1`) returns each round of a consolidation task with its inputs, through the routes the consolidation screen reads. A blinded consolidator gets the same opaque IDs and *Annotator A*, *Annotator B* as in the web interface, and `get_submission` takes an input's `source_submission_id` as it is. Before, such a token could not find these IDs. No route or token scope changed.

### Fixed

- Editor: overlapping findings are told apart (#524). Text that belongs to several findings shows one band per finding inside the highlight, each in its finding's colour, in the same order in every piece (by where the findings start); up to three bands, with four or more colours the top band is striped. Before, such text had the fill of one finding only. Different terms that overlap, or stand next to each other in a sentence (at most 24 characters apart, no sentence end between), never share a colour any more: the colours are chosen once per text, each term keeps the colour of its term when it can and otherwise takes the next free one, and the same term keeps one colour across the text. The same in the editor, the read-only text view and the consolidation editor. Selecting a finding no longer changes the colour of overlapping text; the frame shows the selection. No change to the palette, the lines of the mark states, the line height or the text position.
- **Users** with many accounts: the table shows the first 100 accounts and **Show all {n}**; **Filter users** still searches every account, and an account created on the page stays in view. Every account used to be a row, so with about 2,000 accounts opening **New user…** and typing in it took seconds; in the browser tests the click timed out.
- Translations: a review assigned after **Fix typos…** on a rejected or queried version is a review of the corrected version (review 2 of the lead's pages, F1). **Assign review…** and **Resolve…** › **Assign a new review…** announced *v2* but assigned a review of v1: the reviewer never saw the fix, and when they accepted v1 unchanged the row read *v2 corrected · in review* with nobody to wait on and no next step. The corrected version now counts as the newest text of its translation whenever the version it corrects does, so the row, the assign dialog (which names the version the task is assigned on), the single assignment of the API and the MCP tool `assign_texts` all use it; the reviewer reads *Typos fixed by the project lead on …* in **Translation details**, which no longer runs off the screen at 390 px. A version a lead fixed typos in takes no further review: a new assignment and **Reopen…** of its review are refused with `VARIANT_REVIEW_STALE` (`details.reason` `typos_fixed`, with the corrected version), the text card and **Resolve…** no longer offer that reopen, and **Ask a reviewer to correct…** is offered only at the newest version. A corrected version that a reviewer rejects or queries stays the text to resolve; it never falls back to the text with the typos. Migration 0046 (data only) repairs texts already stuck: a typo fix left *Reviewed* behind a version that was accepted afterwards becomes *Accepted*, as a fix made after the acceptance would be.
- Documents: the **Translation** state of an accepted text whose typos a lead fixed credits the lead (review 2, F5). The phone card read *Accepted, with corrections, v1 → v2, Ana Weber*, naming the reviewer who had accepted v1 unchanged; it reads *Accepted, typos fixed by you, v1 → v2* (stage cell note `typos_fixed`, with the lead under `people`).
- Text card: **History** has a line for **Fix typos…** in the form of the other lead actions, for example *typos fixed in v2 by you, 17 Nov, 17:24: Typo; Grammar* (review 2, F6), and **Resolve…** keeps showing the reviewer's reason after a typo fix.
- Small gaps in feedback (review 2, F7 a to d). **Release…** in the notice of a text card now answers with the message of the bulk action (*Released 1 text.*), and the card's **History** reloads after a pause or release, so the new line is there at once. After **Undo** of a replaced final result, the green line *Final result saved for EN100022 en.* in the card goes; it spoke of the result that is no longer final. **My tasks** at desktop width writes the lead's reason for reopening a task under the task name (*Reopened by the lead on 17 Nov 2026, 14:30: The onset in sentence 2 is missing.*), as it does for a second review and as the phone already did; the **Reopened** badge keeps its popover. A project's only lead who unticks their own **Lead** box or clicks **Remove…** on their row reads *Add another project lead before removing the last lead.* at once, not after confirming *Remove … from the project?*; a system administrator, who may remove the last lead, gets the dialog as before.
- Documents: the text card's **History** keeps a line for each pause of a text by a lead and for each release, with who, date and time and the reason (review 2, F6): *paused by you, 17 Nov, 17:24: The clinic is checking the source text*, *released by you, 17 Nov, 18:02*. Before, History named only the pause in place, filed under **Annotation**, and nothing after the release. The lines carry the tag **Text**: a pause belongs to the text, not to a stage. They come from the audit trail (`text.pause`, `text.release`) as the new kinds `text_paused` and `text_released` of `changes` in `GET …/document-rows/{case}/{language}/submissions`.
- Documents: texts that can still take another annotator while the first is at work can be found (review 2, F4). **Filter** › **Annotation** has the option **Can take another annotator**: every text whose steps include **Assign annotation…**, with its count; with the tab **In progress** it lists exactly the texts that someone works on and that have a free place. It is the new value `can_take_annotator` of the `flags` filter and facet of `document-rows` (the same texts as `step=assign_annotation`, which has no count). At 1440 px such a row keeps the limit in view: *0/1 · max 2* (submitted of the people who hold the text, then the limit) where it read *not started* or *0/1 submitted* like a fully staffed text; the tooltip and the wide table are unchanged. The empty tab **To assign** no longer says *Nothing to assign* while rows elsewhere offer **Assign annotation…**: it reads *No text waits for an assignment*, explains that a text someone works on can take another annotator up to the limit, and offers **Show texts that can take another annotator**. No row moves between tabs.
- Annotation view on a phone: an annotator whose editor was open when the lead paused the text now reads why the save was refused (review 2, F3). At 700 px and below the editor shows one pane at a time, and the banner *Paused by lead: …* sat above the visible **Details** pane: the term search vanished without a word. The **New finding** panel now repeats the line there (*Paused by lead: The clinic is checking the source text. Nothing can be saved now. What you marked is kept until you leave the task.*); it is the same line for a pause from a problem report. Wider windows are unchanged: the banner is in view.
- Documents: a text with an open consolidation keeps it when the text is paused (review 2, F2). The Annotation stage cell replaced a running consolidation by a bare *paused* cell, and Documents reads the open consolidation from that cell: the row said *waiting*, the text card hid the consolidator and offered **Consolidate…**, which the server then refused (*Someone else is already consolidating this text.*), and the Annotation stage read *paused by lead, 2 of 2 submitted* although submitted work is never paused. The cell now stays `consolidating` with its consolidators and counts and names the pause in `note` (`lead_pause`, or the new `report_pause` when the consolidator's problem report pauses the task, which had the same defect). The row reads *consolidating · paused* under **Finalization**, the card keeps the consolidator's row with *Paused by lead* (or *Paused*), the Annotation stage reads *2 of 2 submitted*, and no second consolidation is offered. A paused translation reviewer's row in the card says *Paused by lead* too. In **History**, the lines of a consolidation are filed under **Finalization** instead of **Annotation**.
- Documents, review follow-ups for the lead (#469). A refused **Undo** of **Reopen…** or **Withdraw open tasks…** names the first text in the way and what changed on it, as the Undo of **Change final…** does: *Undo is not possible: 1 of 7 texts changed since (EN100022 en: a task was assigned, reopened, withdrawn or paused, or got a new round). Nothing was undone.* `POST …/bulk-task-actions/undo` lists these texts in `blocked_texts` (with `texts`, the number of texts the action changed), the refusal `BULK_UNDO_STALE` carries that answer as `preview` in its details, and the MCP tool `undo_reopen_or_withdraw` returns `blocked_texts` and names the first text in its note. ### Security

- Handle text change: for a task from proposals, the dialog explains why only Withdraw is possible and what to do next (#235).
- Upload: the Work plan says to check it before importing, sources read "only cases without a translation", and the line next to the import button repeats the plan (#236).
- Editor: the paused banner has its own row under the toolbar; term hits stay visible with the search field in the stacked editor; the Sections panel closes on an outside click; save errors show their text at every width and keep the title. Documents: the header checkbox shows checked when every filtered text is ticked by hand, the distribution proposal names texts, not internal IDs, and the text card spaces its assignment actions. The Assign dialog names a failed load, a failed project list no longer leaves a loading line, and the Documents and My tasks counters update after a closed report or a submitted consolidation.
- An import no longer stops the project while it plans (#209). The preview takes no project lock, and the commit holds it exclusively only for the last part of the writes: about 15 to 19 s instead of over two minutes for 3,000 documents with 10 proposals each. These figures hold for proposal bundles; translation or correction bundles with many per-row updates were not measured. A project change behind the plan is still detected, and the import still applies fully or not at all. A commit also refuses (`UPLOAD_STALE`) when the work plan of a case in the upload changed since it planned: its work plan rows, or a translation review of that case assigned, submitted or decided in between. A commit request with work plan choices checks them against the stored preview instead of parsing the upload again.
- At a width of exactly 700 px the annotation editor collapsed to no width, so the Document tab showed no text (#144).
- The selection bar names what the filters hide, for example "4 texts in 2 cases selected (2 source texts not shown)", and the header checkbox counts texts, not cases (`text_count`, `not_shown_sources`) (#210).
- *Distribute evenly…* replaces the assign dialog instead of opening on top of it; the walk-through goes on from there (#210).
- An Edit & Replace copy is listed with the proposal it replaces, not under *Your own findings*, and the result line counts it as a replaced proposal (#211).
- A Documents row reads **Accept result…** only when submissions also agree on notes and modifier text spans, as the card does; otherwise it reads **Compare results…** (`all_match`) (#211).
- Opening the text list right after a bundle import no longer takes minutes and blocks the project: the query for each document's newest proposal set no longer depends on fresh planner statistics.
- One slow read or one queued writer can no longer stop a project or the instance (#217). Web requests wait at most 20 s for a lock (`ONTOTATOR_LOCK_TIMEOUT_MS`) and run a statement for at most 60 s (`ONTOTATOR_STATEMENT_TIMEOUT_MS`); a full connection pool fails after 10 s. All three answer 503 `PROJECT_BUSY` with `Retry-After`, the work is rolled back, and the user reads that the project is busy and nothing was changed. Jobs, the CLI, migrations and backups have no limit.
- `admin projects create --allowed-roots <id>=` allows every term, as its help says, instead of failing with exit 2 (#208).
- Changing the profile source or the file on the New project form no longer keeps branches, scheme and version chosen for the previous profile (#208).
